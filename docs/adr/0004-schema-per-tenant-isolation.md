# Schema-per-Tenant Isolation

AIARAP expects around 10 Tenants over the next 2-3 years. At that scale, the operational costs that usually rule out schema-per-tenant (Postgres catalog bloat, N-schema migration sprawl, connection-pool complexity) don't apply. Each Tenant gets its own Postgres schema within a shared database instance, giving stronger isolation and much simpler per-tenant backup, export, and deletion (a single `DROP SCHEMA`) than a shared-schema-with-`tenant_id` model would, without the infrastructure cost of a fully separate database per Tenant. Per-tenant custom fields are handled separately via JSONB on a uniform schema (see custom-fields-via-jsonb ADR) rather than by literal per-tenant schema drift, so this decision rests purely on isolation/operability, not on needing structurally different tables per Tenant.

## Reaffirmed: schema-per-tenant vs. single-schema with row-level security

This decision was revisited after a concrete cross-Tenant modeling question came up (the Customer Representative entity, below) that at first looked like an argument for reversing to a single shared schema with Row-Level Security (RLS) by `tenant_id`. It was re-examined against that alternative and reaffirmed, for the following reasons:

- **Triggering case — Customer Representative**: an AIARAP employee, not scoped to any single Tenant, assignable to Tasks that live inside a Tenant's schema. This looked like it required either duplicating Customer Representative records per Tenant schema, or moving to a single shared schema so one `customer_representative` table could serve every Tenant.
- **Resolution without abandoning schema-per-tenant**: Postgres schemas are siblings within one database, not nested — but since every Tenant schema already lives in the *same* shared database instance (per the original decision above), cross-schema references are natively supported: real foreign-key constraints and joins work directly across schemas, no `dblink`/FDW needed. So a single **`global` schema** (alongside each `tenant_x` schema) holds AIARAP-internal, cross-Tenant entities — starting with Customer Representative — and any Tenant schema's tables can hold a plain FK into it (e.g. `tenant_acme.task.customer_rep_id REFERENCES global.customer_representative(id)`). This removes the original objection without changing the isolation model.
- **Development-flexibility tradeoff considered**: single-schema+RLS is generally more development-flexible at scale — one migration path instead of N, native ORM/tooling support, trivial cross-tenant admin queries, simpler local dev/test fixtures. This is real, but it's optimizing for a tenant-count problem (hundreds/thousands of tenants) that AIARAP doesn't have at ~10 Tenants over 2-3 years.
- **Industry practice considered**: most SaaS companies at large scale default to single-schema + a tenant discriminator (RLS or app-level filtering) — e.g. Salesforce's shared, metadata-driven multi-tenant kernel; Supabase's RLS-first design; GitLab.com's single shared schema with `namespace_id` scoping. Schema-per-tenant (or further, database-per-tenant) shows up in products with fewer, larger, longer-lived customers — e.g. Discourse's "multisite" feature (literally one Postgres schema per site in a shared DB); Odoo and Frappe/ERPNext (full database-per-tenant), both ERP-adjacent products with a small-N tenant profile similar to AIARAP's.
- **SAP precedent considered**: SAP's own flagship cloud ERP, S/4HANA Cloud Public Edition, gives each tenant a dedicated HANA tenant database (via HANA's Multi-Database Container feature) with dedicated ABAP application servers — a *stronger* isolation boundary than schema-per-tenant, chosen despite SAP presumably operating at far larger tenant counts than AIARAP. For ERP-adjacent, financially sensitive data — the exact category AIARAP's Tenants already trust SAP with — this weighs isolation-by-construction over shared-schema dev convenience. (SAP C4C's specific isolation mechanism was checked but not confidently confirmed from available sources, so it isn't used as supporting evidence here.)
- **Conclusion**: schema-per-tenant isolation stands. A `global` schema is added to the design for AIARAP-internal entities that span Tenants, starting with Customer Representative.
- **Tenant-side visibility**: a Tenant's Users must only see the Customer Representative(s) assigned to their own Tenant, not AIARAP's full employee roster — this requires an assignment mapping between Tenant and Customer Representative. That mapping lives inside each Tenant's own schema (e.g. `tenant_acme.assigned_customer_representative(customer_rep_id)`, FK into `global.customer_representative(id)`), not as a `(tenant_id, customer_rep_id)` table in the `global` schema — keeping every Tenant-specific fact inside that Tenant's own schema (no `tenant_id` column needed, since the schema boundary already is the Tenant boundary), consistent with how every other Tenant-scoped relationship in the design works. Only the Customer Representative's own master record (name, email, employment status) is genuinely global.

**Update ([ADR-0018](0018-customer-representative-assignment-tenant-approval.md))**: populating this assignment mapping now requires the Tenant's own Admin to approve first, rather than being a unilateral AIARAP-side action.

**Update (table structures session)**: Customer Representative's identity fields (name, email, employment status, etc.) now live on a broader `global.aiarap_staff` table — AIARAP's full internal staff directory, covering employees who never touch a Tenant's environment at all. `global.customer_representative` is now a thin subtype/role-tag on top of it (`staff_id` as its PK), marking which staff are eligible for Tenant-facing assignment. This also gives a proper home to AIARAP-side actors this ADR's design didn't account for — e.g. ADR-0010's "AIARAP employee" who bootstraps a Tenant's first Admin, and the requester on ADR-0018's assignment-request flow — neither of whom is necessarily a Customer Representative themselves.
