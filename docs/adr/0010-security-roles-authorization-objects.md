# Security Roles: SAP-Style Authorization Objects with Derived Roles

AIARAP's role/permission model is fixed and AIARAP-defined for Phase 1 (no Tenant-built custom roles or permissions), but roles are parameterized similarly to SAP's own authorization model rather than being simple flat booleans:

- **Authorization Object**: a reusable, AIARAP-defined type bundling a set of scoping fields (e.g. a "Sales Area" object = `sales_org` + `distribution_channel` + `division`).
- **Permission**: an atomic capability (e.g. "Sales Order Create") that references **at most one** Authorization Object (not many-to-many — a permission needing multiple simultaneous objects is a real SAP capability but out of scope for Phase 1). Holding a Permission is what surfaces the corresponding feature/menu item at all; the Authorization Object's field values then scope what data that Permission can actually touch (e.g. which Customers/Products are searchable). Most Permissions gate a business action performed *as yourself* and so carry a real Authorization Object (`authorization_object_id` set) — but a Permission gating a flat, unscoped meta-action (e.g. [ADR-0011](0011-user-impersonation-audit-trail.md)'s "Impersonate Payer/Vendor User" — a yes/no switch with no business-data dimension to scope by) legitimately has `authorization_object_id` = `NULL`. This is a real category, not a placeholder/workaround: once an impersonation session starts, every subsequent business action is checked against the *impersonated* User's own Roles/Permissions/Authorization Object values, never the initiator's — so the gating Permission itself was never meant to carry a scope.
- **Parent (master) Role**: an AIARAP-defined, fixed bundle of Permissions — this is what determines *what a role can do*, and Tenant/Payer/Vendor Admins cannot alter it.
- **Derived Role**: created by a Tenant Admin, Payer Admin, or Vendor Admin from a Parent Role. A Derived Role always inherits the exact same Permission set as its parent (no permission toggling on derivation) — the Admin creating it only supplies **Authorization Object field values**, i.e. *where/what scope* that access applies to. This mirrors SAP's real derived-role behavior (same transactions as the parent; only org-level authorization values differ per derivation).
- **`role_authorization_value`**: a Derived Role's granted values for an Authorization Object are stored as **multiple rows, OR'd together** (`{role_id, authorization_object_id, criteria: JSONB}`), matching SAP's real multi-line authorization support — this avoids the cross-product leakage a single multi-valued-field row would create (e.g. granting `sales_org IN (1000,2000), division IN (01,02)` as one row would incorrectly also permit combinations like Sales Org 1000 + Division 02, which nobody actually authorized). A blank cell or explicit `*` in a row's criteria means wildcard (any value) for that field — the same convention already used by the AP/RFQ approval matrices, kept consistent across the platform.
- **Multiple Roles per User**: a User can hold more than one Role at once; total access is the union of every assigned Role's Permissions and Authorization Object values. This avoids forcing awkward one-off combined roles for a User who needs more than one area of access (e.g. Sales Order Create scoped to one Sales Area, plus AP approval scoped to a different Cost Center).

## Storage: seeded per-tenant, not a shared `global` copy

Authorization Object, Permission, and Parent Role are fixed/AIARAP-defined, but they are **not** stored once in the `global` schema — each `{tenant}` schema gets its own copy of these rows, seeded via the same migration pipeline that already provisions a new Tenant's schema ([ADR-0004](0004-schema-per-tenant-isolation.md)). Every copy uses the same well-known, fixed UUIDs across all Tenants (e.g. "Sales Order Create" is the same `id` in every schema), so application code can reference a fixed Permission/Role by ID regardless of which Tenant it's running for, while the row itself remains physically local to that Tenant's schema. This preserves "a Tenant's schema is the complete picture of that Tenant" ([ADR-0011](0011-user-impersonation-audit-trail.md)) without introducing a new category of cross-schema FK beyond the one narrow exception ADR-0004 already designed for (Customer Representative) — a dropped/restored Tenant schema stays fully self-contained. The cost: introducing a new fixed Permission/Role later means a migration fanning out to every `{tenant}` schema, the same operational shape ADR-0004 already committed to for schema-per-tenant itself.

## Admin bootstrap and management hierarchy

- An AIARAP employee creates the **first Tenant Admin** for a new Tenant (solves the chicken-and-egg problem: an Access Request normally needs an existing Admin to approve it, so the very first Admin can't come from that flow).
- An existing **Tenant Admin** can create additional Tenant Admins.
- **Tenant Admin** has full create/change/delete authority over **Payer Admin** and **Vendor Admin** accounts.
- **Payer Admin / Vendor Admin** have no authority to create or manage any Admin account (no peer-Admin creation) — they retain their existing, unchanged authority to approve/deny Access Requests and manage regular Users within their own Payer/Vendor organization.
- Terminology note: `CONTEXT.md` previously referenced a "User Admin" role distinct from Payer Admin/Vendor Admin ("cannot manage User Admins per the role matrix") — this was inconsistent terminology for the same Admin role, not a real distinct tier, and is corrected by the hierarchy above.
- Now that a minimal `role`/`user_role` slice exists (`0001-phase-1-table-structures.md`, pulled forward to unblock [ADR-0021](0021-parking-lot.md) items 3/6): "an existing Tenant Admin can create additional Tenant Admins" is enforced as an application-layer check on the `user_role` insert itself — the actor must already hold `tenant_admin` in their own `user_role` rows, except for the bootstrap case above. No cross-schema/global-schema involvement — entirely within the Tenant's own schema.
