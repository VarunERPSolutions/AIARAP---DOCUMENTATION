# Notification Channel

A generic Notification Channel abstraction, paralleling [ADR-0001](0001-payment-provider-abstraction.md)'s Payment Provider interface: Email is the only Phase 1 implementation, SMS is schema-ready but unimplemented, gated by `tenant_settings.sms_notifications_enabled`. This retroactively gives every alert referenced by name earlier this session — Credential Expiry Alert, Card Expiry Alert, AR Clerk notification on SAP write-back failure ([ADR-0019](0019-automatic-card-payment-batch.md)) — an actual mechanism to send through, via `notification_type` as the discriminator rather than a dedicated table per alert.

## Template-driven, Tenant-editable

Two tables: `notification_template` (one row per `notification_type` + `channel`, editable content) and `notification` (insert-only send log, storing the *rendered* result at send time — not just a template reference — so history reflects what was actually sent even if the template is edited afterward).

Templates are seeded with defaults per Tenant at provisioning and can then diverge — same treatment as Finding 2's fixed reference data, but unlike `currency` (globally fixed, never diverges), a Tenant may edit their own copy's wording or branding. This was a deliberate choice over composing content in application code: nothing in this session's alerts needed it yet (they're all internal/operational — AR Clerks, Tenant Admins), but a Payer-facing notification (e.g. the spec's guest-lookup-repeated-failure alert) would want Tenant branding, and building the template layer now avoids a later migration once that need is concrete.

## Polymorphic linkage

`notification.related_entity_type`/`related_entity_id` let a notification point back at whatever triggered it (a `card_payment`, an `ar_reconciliation_account`, a `payer_payment_card`) without a dedicated FK column per possible source — same pattern as `audit_log`.

## Tenant-registered sender identities are domain-level, not per-address

A Tenant can register their own "From" address per notification type (`invoice@tenant.com` instead of an AIARAP-owned domain), but what's actually verified is the **domain**, not each address — matching how AWS SES's DKIM verification actually works: once `tenant.com` is verified, any address at it (`invoice@`, `ar@`, ...) can send without separately re-verifying each one.

**The only information actually collected from the Tenant is the domain itself** (or the desired sender address, from which the domain is derived) — inserted as `notification_sender_identity.domain`. Everything else is *generated by SES and handed back to the Tenant*, not collected: creating the identity returns a set of DKIM CNAME tokens (typically three) plus an optional recommended SPF TXT record, stored as `notification_sender_dns_record` rows and displayed to the Tenant Admin with instructions to add them to their own DNS host — an action that happens entirely outside AIARAP. SES then periodically queries DNS to verify each record independently; `notification_sender_identity.verification_status` only rolls up to `'verified'` once every required record does.

`notification_template.sender_identity_id` + `sender_email` selects which verified domain and which specific address at it a given `(notification_type, channel)` uses (NULL = AIARAP default) — the identity/domain is shared and reusable, the address is per-template, matching the "register a sender by notification" ask without re-verifying per address.

**Fallback rule**: if a template's selected identity isn't `'verified'` at send time (still pending, or failed), the app must fall back to the AIARAP default sender rather than attempting the send — an unverified domain would simply be rejected by the provider outright, not degrade gracefully on its own. `notification.sender_identity_id`/`sender_email` snapshot which one was *actually* used for that specific send, same "store what was actually sent" reasoning already applied to `subject`/`body`.

## Open items

- Retry mechanism for a genuinely failed send (transient provider error, e.g. SES throttling) — `notification.retry_count` exists for tracking, but no retry job/backoff schedule is designed here.
- Email provider specifics (AWS SES vs. another provider) — not decided, though the domain/DKIM design above assumes SES's model specifically.
- The mechanics of *how* AIARAP learns a DNS record has verified (an SES→SNS webhook vs. a polling job) aren't designed here, only the state machine (`pending`/`verified`/`failed`) it drives, at both the record and identity level.
- Whether the SPF TXT record is required or merely recommended, and how AIARAP handles a Tenant who already has an existing SPF record at their domain (merging into one record vs. requiring them to do it themselves) — not resolved.
- SMS implementation itself remains entirely out of scope for Phase 1, per the spec.
