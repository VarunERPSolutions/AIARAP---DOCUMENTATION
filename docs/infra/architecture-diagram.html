VarunERP — Access & Integration Architecture

Three views of the same VPC: how employees reach internal AWS servers over Tailscale, how Tenant systems reach AIARAP's public inbound APIs, and how AIARAP's own Java service reaches out to each Tenant's SAP system. Updated Sep 2026 to match the resolved design (Cognito + API Gateway + Lambda authorizer for inbound; SQS + per-Tenant credentials for Java's nightly outbound extraction, per ADR-0017), shown for two example Tenants.

2 — Tenant integration hub (inbound)

Ten Tenant Salesforce orgs and ten Tenant SAP systems call in to Node; VarunERP's own Salesforce calls its own SAP the same way, since Salesforce can't run a Tailscale client either. Shown for two example Tenants — every additional Tenant repeats the same pattern. There are only 2 inbound REST APIs (node, sap) — every environment is a stage of one of these two, not a separate API. Java is not part of this figure — it has no inbound path at all; see Figure 3.

Listener ports and routing logic

Each backend is one REST API with one deployment (identical resources/methods/integrations across its environments) and one stage per environment. Every stage carries its own gwPort stage variable; the integration URI is http://<nlb-dns>:${stageVariables.gwPort}/..., which API Gateway substitutes per-request from whichever stage actually handled the call. That's what lets 2 REST APIs serve 5 physically distinct listener ports below without needing one API per port — and it's also why the authorizer can read environment straight off requestContext.stage instead of parsing anything.

  • Per-connection isolation: every Tenant gets its own Cognito app client and API key per backend per environment — a leaked credential for one Tenant's connection can't be replayed against another Tenant's data.
  • Prod is the bare subdomain: {subdomain}.aiarap.com = prod, dev.{subdomain}.aiarap.com/qa.{subdomain}.aiarap.com = non-prod — same convention on the SAP side (sap-api.varunerpsolutions.com vs dev.sap-api.varunerpsolutions.com). Each environment is its own API Gateway custom domain object now (not an apex+wildcard pair) since dev/qa route to different stages — a wildcard domain can't pick a stage based on which subdomain was hit.
  • Not the same hostnames as Figure 1: the SAP API domains above are new, genuinely public endpoints — deliberately distinct from sapdev.varunerpsolutions.com, which resolves to an unroutable Tailscale address and stays internal-only.
  • No Java here: the original design had a customer-facing java-api, on the assumption a Tenant's SAP called Java directly. Per ADR-0017, Java is outbound-only nightly batch extraction — see Figure 3.
  • Open item: SAP prod and node prod (HANA instance / dedicated EC2 instance, plus — for SAP — the tailnet-proxy forwarding rule) aren't provisioned yet — everything marked planned/faded above activates once each real instance ID replaces its placeholder.

3 — Java: nightly outbound extraction

A separate mechanism from Figure 2 — Java/Spring Batch (ADR-0017) never receives an inbound call. It runs nightly, calling out to each Tenant's own SAP system to extract Invoices/Bills/RFQs/POs, writes them to that Tenant's own staging tables, then hands off to NestJS over SQS. No Cognito, no API Gateway, no NLB listener — just outbound credentials and a queue.

4 — Example: three calls to add two numbers

Same toy contract on all three routes — POST .../add with {"a": 2, "b": 3}, expecting {"sum": 5} back — so the only thing that varies below is which environment/stage the call reaches and by which path. Each example shows the request at four points: as the caller sends it, what the Lambda authorizer decides, what reaches the NLB, and what the NLB forwards on. All three land on Figure 2's inbound path — Java's outbound flow (Figure 3) doesn't have a request/response shape to walk through the same way, since nothing calls it.

A — Tenant A's Salesforce → Node (dev)

acme's Salesforce calling its dev environment. Client acme-sf-node-dev, scope node.invoke.dev.

① Request as sent by Salesforce — before Lambda runs 
POST /node/add HTTP/1.1
Host: dev.acme.aiarap.com
Authorization: Bearer eyJraWQiOiJhYmMxMjMiLCJhbGciOiJSUzI1NiJ9...<truncated>
x-api-key: 8f3a1c2e-acme-sf-node-dev
Content-Type: application/json

{"a": 2, "b": 3}

Decoded token payload, for reference — API Gateway hasn't touched this yet, it's exactly what Salesforce's HTTP client sent:

{
  "client_id": "acme-sf-node-dev",
  "scope": "https://api.aiarap.com/node/node.invoke.dev",
  "token_use": "access",
  "iss": "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_ExAmPle",
  "exp": 1893456000
}
② The Lambda authorizer's decision

What it receives (abbreviated) — apiId and stage are already resolved by API Gateway before the authorizer runs:

{
  "requestContext": { "apiId": "a1b2c3d4e5", "stage": "dev" },
  "methodArn": "arn:aws:execute-api:us-east-1:043207749006:a1b2c3d4e5/dev/POST/add"
}

What it returns — required scope was node.invoke.dev (backend "node" from apiId, environment "dev" from stage); the token has it, so:

{
  "principalId": "acme-sf-node-dev",
  "policyDocument": {
    "Version": "2012-10-17",
    "Statement": [{ "Action": "execute-api:Invoke", "Effect": "Allow",
      "Resource": "arn:aws:execute-api:us-east-1:043207749006:a1b2c3d4e5/dev/*/*" }]
  },
  "context": { "backend": "node", "environment": "dev", "scope": "node.invoke.dev" }
}
③ Request as it reaches the NLB

The /node base path is already stripped; ${stageVariables.gwPort} resolved to 3001 — node-dev's listener port:

POST /add HTTP/1.1
Host: internal-varunerp-nlb-1a2b3c4d.elb.us-east-1.amazonaws.com:3001
X-Forwarded-Host: dev.acme.aiarap.com
X-Forwarded-For: 203.0.113.42
Content-Type: application/json

{"a": 2, "b": 3}
④ Request as it leaves the NLB

The NLB is Layer 4 — it forwards the TCP connection to the target unchanged, it doesn't rewrite HTTP content. Arrives at i-0e8bb91b84754d419:3001, the node-dev container:

POST /add HTTP/1.1
Host: internal-varunerp-nlb-1a2b3c4d.elb.us-east-1.amazonaws.com:3001
X-Forwarded-Host: dev.acme.aiarap.com
Content-Type: application/json

{"a": 2, "b": 3}

node-dev responds: {"sum": 5}
