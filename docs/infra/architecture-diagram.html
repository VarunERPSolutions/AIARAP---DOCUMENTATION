VarunERP — Access & Integration Architecture

Five views of the same VPC: how developers/infra-admins reach internal AWS servers over Tailscale (narrowed to exactly that, ADR-0038), how Tenant systems reach AIARAP's public inbound APIs, how AIARAP's own Java service both extracts nightly and now also handles real-time SAP calls (ADR-0039), a worked request/response example, and how Payers/Vendors/Tenant Users/AIARAP support staff reach the portal apps themselves over the public internet (ADR-0038). Updated Sep 2026, shown for two example Tenants.

1 — Developer & infra-admin access via Tailscale

Every server-level connection — SSH for a code deploy/debug session, or admin access to SAP HANA/ADS/Postgres RDS — goes through an authenticated WireGuard tunnel, scoped by ACL group; no server accepts direct public connections. This is deliberately narrower than it used to cover (ADR-0038): reaching the portal apps themselves — as a Payer, Vendor, Tenant User, or AIARAP support staff member — no longer goes through Tailscale at all, in any environment. 2 — Tenant integration hub (inbound, machine-to-machine)

Ten Tenant Salesforce orgs and ten Tenant SAP systems call in to Node; VarunERP's own Salesforce calls its own SAP the same way, since Salesforce can't run a Tailscale client either. Shown for two example Tenants — every additional Tenant repeats the same pattern. There are only 2 inbound REST APIs (node, sap) — every environment is a stage of one of these two, not a separate API. This figure is system-to-system only (client_credentials tokens) — human portal/support login is a separate scope on the same Node API, see Figure 5. Java is not part of this figure either — nothing here calls it directly; see Figure 3. The single shared Cognito pool shown below is what's actually live in AWS today; ADR-0040/Figure 7 (confirmed, Terraform drafted but not applied) splits the M2M side into 3 "System Comms" pools by environment instead.

Listener ports and routing logic

Each backend is one REST API with one deployment (identical resources/methods/integrations across its environments) and one stage per environment. Every stage carries its own gwPort stage variable; the integration URI is http://<nlb-dns>:${stageVariables.gwPort}/..., which API Gateway substitutes per-request from whichever stage actually handled the call. That's what lets 2 REST APIs serve 5 physically distinct listener ports below without needing one API per port — and it's also why the authorizer can read environment straight off requestContext.stage instead of parsing anything.

  • Per-connection isolation: every Tenant gets its own Cognito app client and API key per backend per environment — a leaked credential for one Tenant's connection can't be replayed against another Tenant's data.
  • Prod is the bare subdomain: {subdomain}.aiarap.com = prod, dev.{subdomain}.aiarap.com/qa.{subdomain}.aiarap.com = non-prod — same convention on the SAP side (sap-api.varunerpsolutions.com vs dev.sap-api.varunerpsolutions.com). Each environment is its own API Gateway custom domain object now (not an apex+wildcard pair) since dev/qa route to different stages — a wildcard domain can't pick a stage based on which subdomain was hit.
  • Not the same hostnames as Figure 1: the SAP API domains above are new, genuinely public endpoints — deliberately distinct from sapdev.varunerpsolutions.com, which resolves to an unroutable Tailscale address and stays internal-only.
  • No Java here: the original design had a customer-facing java-api, on the assumption a Tenant's SAP called Java directly — never built. Per ADR-0039, Java is now the sole SAP integration layer platform-wide (nightly batch and real-time BAPI/RFC calls), but every path into it originates from AIARAP's own NestJS service, never from a Tenant or any other external caller — see Figure 3.
  • Also not here: human login. This figure's node.invoke.<env> scope is client_credentials only — no person ever holds one of these tokens. Portal/support human login uses two new, separate scopes (node.portal.<env>, node.support.<env>) on this same Node API, added by ADR-0038 — see Figure 5.
  • Open item: SAP prod and node prod (HANA instance / dedicated EC2 instance, plus — for SAP — the tailnet-proxy forwarding rule) aren't provisioned yet — everything marked planned/faded above activates once each real instance ID replaces its placeholder.

3 — Java: SAP integration layer (nightly batch + real-time)

Java is now the sole SAP integration layer platform-wide (ADR-0039), owning two separate mechanisms shown together below. The nightly batch (bottom) still runs on a schedule with no inbound call at all — it extracts Invoices/Bills/RFQs/POs and hands off to NestJS over SQS. Alongside it, Java now also exposes a synchronous internal API (Spring Boot MVC/WebFlux, top) that NestJS calls for live SAP needs — starting with ADR-0029's checkout-time pricing simulation and Sales Order creation. Both paths default to BAPI/RFC via SAP's JCo connector (OData as a per-call fallback), and both are reachable only from inside AIARAP's own VPC — no Cognito, no API Gateway, no NLB listener, no Tenant or public caller either way.

4 — Example: three calls to add two numbers

Same toy contract on all three routes — POST .../add with {"a": 2, "b": 3}, expecting {"sum": 5} back — so the only thing that varies below is which environment/stage the call reaches and by which path. Each example shows the request at four points: as the caller sends it, what the Lambda authorizer decides, what reaches the NLB, and what the NLB forwards on. All three land on Figure 2's inbound path — Java (Figure 3) isn't walked through the same way here: its real-time calls do have a request/response shape now (ADR-0039), but they're internal-only (NestJS→Java→SAP), never Cognito/API-Gateway-mediated like these three.

A — Tenant A's Salesforce → Node (dev)

acme's Salesforce calling its dev environment. Client acme-sf-node-dev, scope node.invoke.dev.

① Request as sent by Salesforce — before Lambda runs 
POST /node/add HTTP/1.1
Host: dev.acme.aiarap.com
Authorization: Bearer eyJraWQiOiJhYmMxMjMiLCJhbGciOiJSUzI1NiJ9...<truncated>
x-api-key: 8f3a1c2e-acme-sf-node-dev
Content-Type: application/json

{"a": 2, "b": 3}

Decoded token payload, for reference — API Gateway hasn't touched this yet, it's exactly what Salesforce's HTTP client sent:

{
  "client_id": "acme-sf-node-dev",
  "scope": "https://api.aiarap.com/node/node.invoke.dev",
  "token_use": "access",
  "iss": "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_ExAmPle",
  "exp": 1893456000
}
② The Lambda authorizer's decision

What it receives (abbreviated) — apiId and stage are already resolved by API Gateway before the authorizer runs:

{
  "requestContext": { "apiId": "a1b2c3d4e5", "stage": "dev" },
  "methodArn": "arn:aws:execute-api:us-east-1:043207749006:a1b2c3d4e5/dev/POST/add"
}

What it returns — required scope was node.invoke.dev (backend "node" from apiId, environment "dev" from stage); the token has it, so:

{
  "principalId": "acme-sf-node-dev",
  "policyDocument": {
    "Version": "2012-10-17",
    "Statement": [{ "Action": "execute-api:Invoke", "Effect": "Allow",
      "Resource": "arn:aws:execute-api:us-east-1:043207749006:a1b2c3d4e5/dev/*/*" }]
  },
  "context": { "backend": "node", "environment": "dev", "scope": "node.invoke.dev" }
}
③ Request as it reaches the NLB

The /node base path is already stripped; ${stageVariables.gwPort} resolved to 3001 — node-dev's listener port:

POST /add HTTP/1.1
Host: internal-varunerp-nlb-1a2b3c4d.elb.us-east-1.amazonaws.com:3001
X-Forwarded-Host: dev.acme.aiarap.com
X-Forwarded-For: 203.0.113.42
Content-Type: application/json

{"a": 2, "b": 3}
④ Request as it leaves the NLB

The NLB is Layer 4 — it forwards the TCP connection to the target unchanged, it doesn't rewrite HTTP content. Arrives at i-0e8bb91b84754d419:3001, the node-dev container:

POST /add HTTP/1.1
Host: internal-varunerp-nlb-1a2b3c4d.elb.us-east-1.amazonaws.com:3001
X-Forwarded-Host: dev.acme.aiarap.com
Content-Type: application/json

{"a": 2, "b": 3}

node-dev responds: {"sum": 5}

5 — Public portal & support access

Designed together, now consolidated in ADR-0038: how a Payer, Vendor, or Tenant User reaches the portal (react-external-app), and how AIARAP's own support staff reach their separate tool (react-support-app) — both public internet, both across all three environments, neither ever touching Tailscale. react-external-app was later reopened within that same ADR — per-Tenant-branded domain instead of one shared portal.aiarap.com, Cognito split into 3 environment-scoped pools instead of one shared pool. react-support-app is unaffected and still matches this figure exactly as drawn.
