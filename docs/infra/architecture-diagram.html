VarunERP — Access & Integration Architecture

Two views of the same VPC: how employees reach internal AWS servers over Tailscale, and how customer systems reach VarunERP's public APIs. Updated Sep 2026 with the customer-integration hub design (Cognito + API Gateway + Lambda authorizer), shown for two example customers.

1 — Employee access via Tailscale

Every employee reaches internal servers through an authenticated WireGuard tunnel, scoped by ACL group. No server accepts direct public connections.

2 — Customer integration hub

Ten customer Salesforce orgs and ten customer SAP systems call in to Node/Java; VarunERP's own Salesforce calls its own SAP the same way, since Salesforce can't run a Tailscale client either. Shown for two example customers — every additional customer repeats the same pattern. There are only 3 REST APIs (node, java, sap) — every environment is a stage of one of these three, not a separate API.

Listener ports and routing logic

Each backend is one REST API with one deployment (identical resources/methods/integrations across its environments) and one stage per environment. Every stage carries its own gwPort stage variable; the integration URI is http://<nlb-dns>:${stageVariables.gwPort}/..., which API Gateway substitutes per-request from whichever stage actually handled the call. That's what lets 3 REST APIs serve 8 physically distinct listener ports below without needing one API per port — and it's also why the authorizer can read environment straight off requestContext.stage instead of parsing anything.

  • Per-connection isolation: every customer gets its own Cognito app client and API key per backend per environment — a leaked credential for one customer's Node connection can't be replayed against their Java connection or another customer's data.
  • Prod is the bare subdomain: custXX.aiarap.com = prod, dev.custXX.aiarap.com/qa.custXX.aiarap.com = non-prod — same convention on the SAP side (sap-api.varunerpsolutions.com vs dev.sap-api.varunerpsolutions.com). Each environment is its own API Gateway custom domain object now (not an apex+wildcard pair) since dev/qa route to different stages — a wildcard domain can't pick a stage based on which subdomain was hit.
  • Not the same hostnames as Figure 1: the SAP API domains above are new, genuinely public endpoints — deliberately distinct from sapdev.varunerpsolutions.com, which resolves to an unroutable Tailscale address and stays internal-only.

3 — Example: three calls to add two numbers

Same toy contract on all three routes — POST .../add with {"a": 2, "b": 3}, expecting {"sum": 5} back — so the only thing that varies below is which backend the call reaches and by which path. Each example shows the request at four points: as the caller sends it, what the Lambda authorizer decides, what reaches the NLB, and what the NLB forwards on.

A — Customer A's Salesforce → Node (dev)

cust01's Salesforce calling its dev environment. Client cust01-sf-node-dev, scope node.invoke.dev.

① Request as sent by Salesforce — before Lambda runs 
POST /node/add HTTP/1.1
Host: dev.cust01.aiarap.com
Authorization: Bearer eyJraWQiOiJhYmMxMjMiLCJhbGciOiJSUzI1NiJ9...<truncated>
x-api-key: 8f3a1c2e-cust01-sf-node-dev
Content-Type: application/json

{"a": 2, "b": 3}

Decoded token payload, for reference — API Gateway hasn't touched this yet, it's exactly what Salesforce's HTTP client sent:

{
  "client_id": "cust01-sf-node-dev",
  "scope": "https://api.aiarap.com/node/node.invoke.dev",
  "token_use": "access",
  "iss": "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_ExAmPle",
  "exp": 1893456000
}
② The Lambda authorizer's decision

What it receives (abbreviated) — apiId and stage are already resolved by API Gateway before the authorizer runs:

{
  "requestContext": { "apiId": "a1b2c3d4e5", "stage": "dev" },
  "methodArn": "arn:aws:execute-api:us-east-1:043207749006:a1b2c3d4e5/dev/POST/add"
}

What it returns — required scope was node.invoke.dev (backend "node" from apiId, environment "dev" from stage); the token has it, so:

{
  "principalId": "cust01-sf-node-dev",
  "policyDocument": {
    "Version": "2012-10-17",
    "Statement": [{ "Action": "execute-api:Invoke", "Effect": "Allow",
      "Resource": "arn:aws:execute-api:us-east-1:043207749006:a1b2c3d4e5/dev/*/*" }]
  },
  "context": { "backend": "node", "environment": "dev", "scope": "node.invoke.dev" }
}
③ Request as it reaches the NLB

The /node base path is already stripped; ${stageVariables.gwPort} resolved to 3001 — node-dev's listener port:

POST /add HTTP/1.1
Host: internal-varunerp-nlb-1a2b3c4d.elb.us-east-1.amazonaws.com:3001
X-Forwarded-Host: dev.cust01.aiarap.com
X-Forwarded-For: 203.0.113.42
Content-Type: application/json

{"a": 2, "b": 3}
④ Request as it leaves the NLB

The NLB is Layer 4 — it forwards the TCP connection to the target unchanged, it doesn't rewrite HTTP content. Arrives at i-0e8bb91b84754d419:3001, the node-dev container:

POST /add HTTP/1.1
Host: internal-varunerp-nlb-1a2b3c4d.elb.us-east-1.amazonaws.com:3001
X-Forwarded-Host: dev.cust01.aiarap.com
Content-Type: application/json

{"a": 2, "b": 3}

node-dev responds: {"sum": 5}

C — VarunERP's own Salesforce → SAP (dev)

Flow 2 — VarunERP's internal Salesforce dev org calling its own SAP dev system. Client varunerp-sf-sap-dev, scope sap.invoke.dev. Root-mapped domain, no base path to strip. Illustrative only: SAP's own "add" would really be an RFC/OData call, not a plain REST body — kept as JSON here for a consistent example across all three routes.

Content-Type: application/json

{"a": 2, "b": 3}

}

Required scope sap.invoke.dev — present, so Allow:

  "principalId": "varunerp-sf-sap-dev",
  "policyDocument": {
    "Version": "2012-10-17",

      "Resource": "arn:aws:execute-api:us-east-1:043207749006:k1l2m3n4o5/dev/*/*" }]

③ Request as it reaches the NLB

gwPort resolved to 8083 — sap-dev's listener port, the same port var.sap_environments.dev.port sets in Terraform:

POST /add HTTP/1.1

④ Request as it leaves the NLB

Arrives at the tailnet-proxy EC2, port 8083 — this is as far as the NLB is involved. From here the proxy forwards it over the Tailscale tunnel to sapdev.varunerpsolutions.com:3200, outside this walkthrough's scope:

POST /add HTTP/1.1
Host: internal-varunerp-nlb-1a2b3c4d.elb.us-east-1.amazonaws.com:8083
X-Forwarded-Host: dev.sap-api.varunerpsolutions.com
Content-Type: application/json

{"a": 2, "b": 3}

SAP dev responds (via the tailnet-proxy, unwound back through the same path): {"sum": 5}
