# Scheduled Jobs

Catalog of every scheduled/background job referenced across the table-structures design (`0001-phase-1-table-structures.md`), consolidated here for visibility instead of scattered inline notes. Each job is tiered per [ADR-0017](../adr/0017-sap-batch-extraction-java-spring-batch.md): **NestJS** for frequent/incremental/lightweight work, **Java + Spring Batch** for heavy nightly-bulk work with chunking/checkpoint/restart needs. Most jobs below are cron-scheduled or event-driven; **SAP Org Structure Extraction** is the one exception — deliberately **ad hoc/on-demand** (Admin-triggered), not on any recurring cadence, since org structure changes rarely enough that a daily/nightly cycle would be pure overhead.

## Superseded: Customer Representative Assignment Expiry job / AIARAP Staff Termination Cascade

Both were designed earlier in this session as scheduled/event-triggered jobs that *wrote* denormalized state (flipping `assigned_customer_representative.is_active := false`) — one on `valid_upto` elapsing, one cascading a staff termination across every `{tenant}` schema. Both are **superseded by a live-check approach** instead: rather than writing the consequence of expiry/termination into every affected row ahead of time, whatever evaluates "is this Customer Representative currently allowed to act in this Tenant" checks, at that moment:

```
assigned_customer_representative.is_active
  AND (assigned_customer_representative.valid_upto IS NULL OR assigned_customer_representative.valid_upto > now())
  AND global.aiarap_staff.employment_status = 'active'   -- cross-schema join via global.customer_representative
```

No scheduled writes, no cross-schema fan-out, no reconciliation-job safety net needed — the check is always correct because it's evaluated live rather than cached. See the "Live-check convention" note on `assigned_customer_representative` in `0001-phase-1-table-structures.md` for where this is enforced (impersonation session start, and — to close the mid-session gap — every impersonation action, reusing ADR-0011's existing per-action middleware).

**Cognito, as defense-in-depth (not the primary mechanism)**: on termination, the app also calls `AdminDisableUser` (blocks future logins) and `AdminUserGlobalSignOut` (revokes already-issued tokens) against that staff member's Cognito identity. This closes the authentication side; the live DB check above closes the authorization side and is what actually stops an in-progress impersonation session, since Cognito token validity alone can't be trusted for a security-sensitive flow like impersonation — the app re-checks server-side regardless of what a still-valid token claims.

## Currency Exchange Rate Extraction — detail

Added alongside the `currency`/`currency_exchange_rate` tables in the Tenancy & Identity domain (`0001-phase-1-table-structures.md`). Runs once daily per Tenant, pulling that Tenant's configured SAP exchange rates (rate type, from/to currency, rate date, rate value) and upserting into `currency_exchange_rate`. AIARAP reflects SAP's own configured rates as-is rather than sourcing or computing rates independently — consistent with AIARAP extracting from Tenants' systems of record rather than replacing them.

Placed at NestJS/incremental tier for now: exchange rate tables are typically small (a handful of currency pairs × rate types per day, not bulk transactional volume), so Spring Batch's chunking/restart machinery isn't obviously justified here the way it is for nightly Bill/Invoice/RFQ/PO extraction (ADR-0017). Revisit if a Tenant's SAP exchange rate table turns out to be unexpectedly large (e.g. daily rates across many currency pairs going back years, pulled in full rather than incrementally).

## Invoice Type Extraction — detail

Added alongside the `invoice_type` table in the Core AR/AP domain (`0001-phase-1-table-structures.md`). Runs daily per Tenant, pulling that Tenant's actual configured SAP billing types (code + name, SAP TVFK-equivalent) and upserting into `invoice_type` by `code`. Unlike `currency` (a fixed ISO standard seeded identically into every Tenant schema), billing types are customized per SAP implementation — a Tenant may have defined its own Z-type codes — so this is extracted per Tenant rather than seeded, same reasoning as Currency Exchange Rate Extraction. Placed at the same NestJS/incremental tier for the same reason: a handful of billing-type rows per Tenant, not bulk transactional volume.

## Payer/Customer Extraction — detail

Also folded into the **Nightly Bulk SAP/Salesforce Extraction** batch — the same gap Product Extraction closed, but more foundational: `payer`/`payer_sales_area`/`payer_company_code`/`payer_hierarchy` had no documented extraction mechanism at all, despite being the master data almost every other entity in this doc references via FK (Invoices, Sales Orders, Payments, stored cards/bank accounts — all of them).

**What's pulled**: dual-sourced like `payer` itself is designed — SAP (KNA1 general data, KNVV Sales Area data, KNB1 Company Code data, KNVH Customer Hierarchy) when `tenant_settings.sap_system_of_record_enabled`, or the Salesforce-equivalent objects when `tenant_settings.salesforce_system_of_record_enabled` — both, if a Tenant has both enabled, since a Payer can legitimately be sourced from either system per `payer`'s own "at least one source ID present" design.

**Promotion order matters here specifically**: Payer/Customer must promote from staging into final domain tables **before** every other entity extracted in this same nightly run — Invoice's, Sales Order's, and every payment-related table's composite FKs into `payer_company_code`/`payer_sales_area` would otherwise fail to promote against a Payer that doesn't exist yet. This is the one entity in this batch where step ordering isn't just a performance nicety.

**`payer_hierarchy`'s time-sliced validity** (non-overlapping `valid_from`/`valid_to` per Payer/Sales Area combo) is enforced at the application layer during promotion, same "app-layer validation, not a DB constraint" treatment already established for that table.

Same staging → promotion flow as every other entity on this path (ADR-0017): raw extracted rows land in staging only, a separate NestJS-owned promotion step applies `custom_fields` JSONB mapping and validation before writing to `payer`/`payer_sales_area`/`payer_company_code`/`payer_hierarchy` directly.

## Product Extraction — detail

Folded into the existing **Nightly Bulk SAP/Salesforce Extraction** batch (Java + Spring Batch, ADR-0017) rather than a new dedicated job — a Tenant's product catalog can run to thousands of SKUs, the same bulk-volume/restart-safety justification that already put Invoices/Bills/RFQs/POs on this path rather than a lightweight NestJS incremental job.

**What's pulled**: SAP MARA/MAKT (`product`'s general/description data), MVKE (`product_sales_org`'s Sales Org/Distribution Channel data), and MARM (`product_uom`'s alternate order units) — via bulk OData, same mechanism as every other SAP-sourced entity on this path.

**Same staging → promotion flow as every other entity here** (ADR-0017): the Java service writes raw extracted rows into per-Tenant staging tables only, never `product`/`product_sales_org`/`product_uom` directly; a separate NestJS-owned promotion step (triggered by the same "batch complete" SQS event, per Tenant/entity/run) applies `custom_fields` JSONB mapping and validation before moving staged rows into the real domain tables. Unlike Bill/RFQ, there's no Owner-defaulting step — Product has no Owner concept.

**What this job does NOT cover**:
- `product_image` — Tenant-uploaded images are captured directly through the portal, not extracted from SAP; SAP-sourced images/drawings are fetched live at display time (never cached), per ADR-0029's Product Catalog design. Neither path touches this batch.
- `product_sales_org.list_price`/`product_payer_price` — a separate, dedicated **List Price Extraction** job (below), NestJS/incremental tier, not this one. Pricing condition records are a different SAP data source than the material master/sales-org/UOM data this job pulls, and change on a different cadence.

**Incremental updates during the day**: not built for Phase 1 — Product master data (descriptions, UOM, Sales Org listing) changes infrequently enough that the nightly pull is treated as sufficient, unlike Invoice/payment data which genuinely needs the Incremental Sync job's near-real-time deltas. Revisit if a Tenant's catalog turns out to change mid-day often enough that this becomes a real gap.

## List Price Extraction — detail

Added alongside `product_sales_org.list_price`/`product_payer_price` in the Product Catalog domain (`0001-phase-1-table-structures.md`), closing a real gap in ADR-0029's design: pricing is never computed or stored locally for real (the authoritative price always comes from the live `BAPI_SALESORDER_SIMULATE` call at cart/checkout time), but that left catalog *browsing* — before anything is added to a cart — with no price to show at all.

**Two extraction scopes in one job**: pulls SAP pricing condition records and populates two different grains —

- **Sales-Area-level** (`product_sales_org.list_price`/`list_price_currency`/`list_price_extracted_at`) — a general indicative price per Product + Sales Org + Distribution Channel, the default shown to any Payer browsing that Sales Area's catalog.
- **Customer-specific** (`product_payer_price`) — a more specific override where a Tenant's SAP has customer-specific pricing configured (Customer-Material Info Record-equivalent) for a given Product + Payer + Sales Area. Checked **first** by the catalog display logic; falls back to the Sales-Area-level price when no override row exists for that Payer.

**Both are indicative only, never authoritative** — same "extracted, not live-called" pattern as Currency Exchange Rate/Invoice Type Extraction, and same NestJS/incremental tier for the same reason (a bounded number of Product/Sales-Area/Payer combinations, not bulk transactional volume). The real price a Payer actually pays can legitimately differ from whichever indicative price was shown while browsing — scale-quantity discounts, active promotions, and tax are all only known once the live simulation actually runs against the specific cart contents.

## SAP Org Structure Extraction — detail

Extracts the Tenant's own SAP organizational structure master data (Company Codes, Sales Orgs, Plants, Purchasing Orgs, and their assignment tables — `company_code`/`sales_org`/`plant`/`company_code_plant`/`sales_org_distribution_channel_plant`/`purchase_org`/`purchase_org_plant`/`purchase_org_company_code`, all designed alongside ADR-0029's Sales Order checkout work) — the reference data every Company-Code/Sales-Org/Plant-scoped feature in this doc (down payment gating, Stripe Connect, minimum payment amounts, catalog listing, delivering-plant assignment) ultimately depends on existing. `purchase_org`/`purchase_org_plant`/`purchase_org_company_code` are AP/Vendor-domain master data pulled here anyway, alongside their AR-side counterparts, since it's the same org-structure config regardless of which domain eventually consumes it — this doesn't reopen AP/Vendor's own deferred status (parking lot item 11), it just avoids leaving master data half-extracted while genuinely AP-specific work (transactional Vendor/Bill/RFQ tables) stays deferred.

**Deliberately ad hoc, not scheduled** — the one job in this catalog with no recurring cadence at all. A Tenant's org structure (how many Company Codes, Sales Orgs, Plants, Purchasing Orgs they have, and how those are assigned to each other) changes on the order of once every few months to years, not daily — a cron cadence here would just be near-permanently-idle overhead. Instead, an Admin (AIARAP staff, during Tenant onboarding or when a Tenant reports adding a new legal entity/plant) triggers this job manually.

**Upserts only the SAP-descriptive fields, never AIARAP-managed operational flags**: a re-run refreshes `code`/`name` (and the assignment tables' membership) from SAP, but must never overwrite `company_code.down_payment_configured`/`down_payment_verified_at`/`_by`, the `stripe_*` fields, or `minimum_{card,ach,sepa}_payment_amount` — those are AIARAP-side operational state with no SAP equivalent, set through their own dedicated flows (manual verification, Stripe Connect OAuth, Tenant configuration), not derived from this extraction.

**Open item**: exact SAP condition type(s)/table(s) to extract from for each scope (e.g. which condition type represents the "list price" for Sales-Area-level vs. which represents a customer-specific agreement) isn't specified here — version/implementation-dependent, left for implementation-time verification, same treatment as other exact SAP specifics in this doc.

## Credential Expiry Alert — detail

Runs once daily across every Tenant, checking both `sap_credential_updated_at + sap_credential_validity_days` and `salesforce_credential_updated_at + salesforce_credential_validity_days` in the same pass (one combined job rather than two separate ones like the OAuth refresh jobs, since this is a lightweight daily check rather than a per-minute one, and a Tenant Admin shouldn't get two separate emails on the same day for what's functionally the same alert type). When either credential's expiry date is within 10 days, sends a Notification (Email, the only Notification Channel implementation in Phase 1) to that Tenant's Admin(s) — and **repeats every day** thereafter, not just once, since the job re-evaluates the same condition daily and it stays true until the credential is actually rotated. The alert naturally stops the day `*_credential_updated_at` changes (the Admin updated the credential), which pushes the expiry window back out past the 10-day threshold — no separate "already alerted" flag needed, since the underlying condition itself resolves.

**Resolved**: identifying "that Tenant's Admin(s)" is now a real query against the minimal `role`/`user_role` slice pulled forward into the Tenancy & Identity domain specifically to unblock this and the AR Clerk write-back-failure fallback (ADR-0019) — `SELECT app_user_id FROM user_role JOIN role ON role.id = user_role.role_id WHERE role.code = 'tenant_admin'`, scoped to that Tenant's schema. See `0001-phase-1-table-structures.md`.

**Open question, not yet resolved**: `*_credential_validity_days` is nullable (a Tenant may not have a known/enforced password-expiry policy on their SAP/Salesforce side, especially for OAuth2/certificate auth where "password validity" may not apply the same way). The job should presumably skip the check entirely when `*_credential_validity_days IS NULL` rather than alerting — worth confirming that's the intended behavior when we revisit this table.

## Automatic Card Payment Batch — detail

Full design in [ADR-0019](../adr/0019-automatic-card-payment-batch.md). Runs daily (proposed cadence, not firmly committed) per Tenant, scanning every open Invoice: resolves the Invoice's Payer, finds an eligible `payer_payment_card` (including a parent's card shared via `allow_child_use`, resolved through `payer_hierarchy`) with a matching `payer_card_payment_policy` (Invoice type allowed, amount under `max_amount_per_charge`), then charges it via the Payment Provider interface (ADR-0001).

Tiered as **Java + Spring Batch**, not NestJS — an exception to the usual per-invoice-volume reasoning in ADR-0017, justified instead by restart-safety: a mid-run crash must never double-charge an Invoice, which is exactly what Spring Batch's chunk/checkpoint/restart model guarantees.

Every attempt (success or failure) is logged to `card_payment_attempt`; a successful charge additionally creates a `card_payment` row and triggers the SAP write-back, which retries a fixed number of times before falling back to notifying the Invoice's Payer's AR Clerk — resolved via `payer_company_code.accounting_clerk_user_id`, a direct FK to `app_user(id)` rather than a Role lookup, chosen specifically so write-back failures route to whichever Tenant employee actually owns that Payer's AR relationship instead of inundating one Tenant Admin (see ADR-0019 for the full state machine and open questions — exact retry count/backoff, and the fallback when no AR Clerk is assigned).

A cross-currency comparison against `payer_card_payment_policy.max_amount_currency` uses today's rate from `currency_exchange_rate` (parking lot item 1, resolved). An Invoice with a matching card/policy that still fails the threshold check — either genuinely over the (converted) amount, or because no exchange rate was available — is upserted into `card_payment_threshold_exceeded` rather than silently skipped, which feeds the Card Payment Threshold Alert job below.

**Resolved**: `invoice_id` on both tables now has a real FK — `invoice` was designed later in this same session (Core AR/AP domain, `0001-phase-1-table-structures.md`; parking lot item 8, resolved). The fallback notification path (when `accounting_clerk_user_id IS NULL`, notifying the Tenant's Admin instead) is also resolved — same `role`/`user_role` lookup as the Credential Expiry Alert job above.

## Card Payment Threshold Alert — detail

Full design in [ADR-0019](../adr/0019-automatic-card-payment-batch.md). Runs daily, per Tenant: queries `card_payment_threshold_exceeded WHERE resolved_at IS NULL`, groups the affected Invoices by AR Clerk (`payer_company_code.accounting_clerk_user_id`), and sends one daily digest Notification (Email, via the Notification Channel, [ADR-0026](../adr/0026-notification-channel.md)) per Clerk listing every Invoice currently blocked from auto-pay and why (`skip_reason`). Repeats daily for as long as `resolved_at` stays NULL — same "condition self-resolves, no separate already-alerted flag" convention as the Credential Expiry Alert and Card Expiry Alert jobs.

Kept as its own NestJS job rather than folded into the Automatic Card Payment batch itself — separates "detect and flag" (Spring Batch, money-movement-adjacent) from "notify" (NestJS, no money-movement stakes), consistent with how other jobs in this domain are tiered.

## Card Expiry Alert + Stripe Card-Data Webhook Sync — detail

Full design in [ADR-0020](../adr/0020-card-expiry-alert-and-stripe-sync.md). Two paired mechanisms:

- **Card Expiry Alert** (NestJS, daily): proactively flags any active `payer_payment_card` within 10 days of its stored expiry — same threshold and "repeats daily until resolved" convention as the Credential Expiry Alert job above. Notifies every distinct AR Clerk (`payer_company_code.accounting_clerk_user_id`) across the card's Payer's Company Codes, deduped — same recipient mechanism as ADR-0019's SAP write-back failure alert, and the same open fallback question (no AR Clerk assigned → Tenant Admin, blocked on the undrafted Security & Roles domain).
- **Stripe Card-Data Webhook Sync** (NestJS, event-driven, not cron): Stripe's Network Tokens/Card Account Updater can silently refresh a stored card's expiry/PAN behind the scenes. This handler listens for Stripe's card-update event and refreshes `card_exp_month`/`card_exp_year`/`card_last4`/`card_brand` on the matching `payer_payment_card` row (matched via `provider_payment_method_ref`), keeping the Card Expiry Alert's data source current so it only fires for cards Stripe didn't manage to auto-refresh in time.

**Multi-tenant routing (ADR-0032 update: per Company Code, not per Tenant)**: Stripe webhooks arrive at one global endpoint, but AIARAP is schema-per-tenant, and not every Company Code uses Stripe at all (`company_code.stripe_enabled`) — all three Stripe-related jobs above only run for Company Codes where it's true, and all Stripe-related tables (`payer_payment_card`, `payer_bank_account`, `payer_card_payment_policy`, `card_payment`, `card_payment_attempt`, `bank_debit_payment`, `bank_debit_payment_attempt`, `payment_provider_webhook_event`) live in `{tenant}` schemas, never `global`. The one exception is a routing-only lookup: `global.stripe_account_routing` (replacing the single-column pointer that used to live on `global.tenant_registry`, since a Tenant can now own several Connected Account IDs — one per Company Code) holds nothing but each opaque account ID mapped to its owning `tenant_registry_id` (no config, no credentials) purely so the webhook receiver can resolve the `{tenant}` schema from the event's connected account ID before it can query anything tenant-specific — the authoritative, app-facing copy of each ID lives on that Company Code's own `company_code.stripe_connected_account_id`, kept in sync with its routing-table row at write time. Once resolved, the event is logged to that schema's `payment_provider_webhook_event` table (`UNIQUE(provider, provider_event_id)` for idempotency against Stripe redeliveries) before processing it.

**Open item**: the exact Stripe webhook event name/payload to key the sync off isn't pinned down yet — verify against the current Stripe API at implementation time.

## SAP Payment Webhook — detail

Full design in [ADR-0022](../adr/0022-sap-payment-webhook.md). Event-driven (NestJS, not cron): a Tenant's own SAP system pushes payments it posted natively (bank transfer, check, cash) as they happen, rather than AIARAP waiting for the next Invoice sync to discover them. Scoped to **SAP-native payments only** — SAP never sends an AIARAP-originated card payment, so every resulting `payment` row has `source = 'sap_native'` by construction.

Routing doesn't need a global lookup like the Stripe webhook does — AIARAP issues the webhook URL itself, with the Tenant's existing `subdomain` embedded in the path. Authenticated via a **bearer token** (`tenant_settings.sap_webhook_secret_ref`, Secrets Manager ARN) — chosen over HMAC signing since it matches what SAP's HTTP destination/CPI configuration supports natively, with no custom signing code required. Logged to `sap_webhook_event` (idempotent on `sap_message_id` when SAP supplies one), then processed into `payment` — `payment`'s own `(invoice_id, sap_clearing_document, sap_clearing_document_year)` unique index is the ultimate idempotency backstop regardless.

**Resolved**: the actual calling mechanism is an **AIARAP-built SAP program/package**, deployed via transport onto each Tenant's system — not something each Tenant has to build themselves. This narrows the remaining risk to just whether a Tenant's SAP system has any outbound HTTP client capability at all; the scheduled Invoice sync remains the fallback discovery path for `sap_native` payments for that residual case.

## Salesforce AppExchange Integration — detail

Full design in [ADR-0027](../adr/0027-salesforce-appexchange-integration.md). Event-driven (NestJS, not cron): a Tenant's installed AIARAP AppExchange package pushes events as they happen — broader in scope than the SAP webhook (not payment-specific; Salesforce is an alternate system of record for the whole platform), gated by `tenant_settings.salesforce_app_enabled`.

Distribution is Salesforce's own standardized channel (a versioned managed package via AppExchange), and authentication is **OAuth 2.0** (`salesforce_app_client_id`/`salesforce_app_client_secret_ref`, a different credential pair from the existing outbound-extraction Salesforce credentials on `tenant_settings`) via Salesforce's native Named/External Credentials — a stronger security posture than the SAP webhook's bearer token, since Salesforce doesn't have SAP's custom-signing-code constraint. Routing follows the same URL-embedded-subdomain pattern as the SAP webhook. Logged to `salesforce_webhook_event`, structurally separate from both `sap_webhook_event` and `payment_provider_webhook_event` — a third distinct integration boundary.

**Open item**: the exact event types the package will send aren't enumerated yet — this establishes the generic mechanism, not the specific integrations built on it.

## AR Reconciliation Batch — detail

Full design in [ADR-0023](../adr/0023-ar-reconciliation-batch.md). Compares each Tenant's SAP-side open AR balance against AIARAP's own `invoice.open_amount`, grained by **Payer + Company Code + Currency** (amounts in different currencies for the same Payer/Company Code can't be combined into one number, so a Payer with both USD and EUR opens gets two account rows). Every account gets a row on every run — including zero-variance ones — so reconciliation history/trend ("has this account been clean for the last 30 runs") is a direct query, not inferred from an absence of rows. Document-level drill-down (`ar_reconciliation_discrepancy`) classifies each contributing Invoice as `amount_mismatch`, `missing_in_aiarap` (SAP has it, AIARAP's extraction hasn't caught up), or `missing_in_sap` (AIARAP shows it open, SAP's current open-item list doesn't).

Tiered NestJS, not Spring Batch — no money moves and no restart-safety stakes, same category as Currency Exchange Rate Extraction and Invoice Type Extraction.

**Real-time trigger, alongside the scheduled sweep**: `ar_reconciliation_run.trigger_type` distinguishes a full `'scheduled'` sweep from a `'webhook_triggered'` run scoped to just one account, fired immediately when the SAP Payment Webhook or Salesforce AppExchange package pushes balance data (ADR-0022/0027's "critical jobs carry richer payloads" principle). No merge/precedence logic is needed between the two — a scheduled run always wins on freshness by construction (it pulls live from SAP at the moment it runs), so the webhook-triggered run's actual value is narrowing the detection window between scheduled runs, not improving the scheduled run's own number.

## Stripe Payout Reconciliation — detail

Full design in [ADR-0025](../adr/0025-stripe-payout-reconciliation.md). Extracts Stripe's daily Payout + Balance Transaction data per Company Code (ADR-0032 update — only Company Codes with `company_code.stripe_enabled`, one Stripe Connected Account per Company Code, not per Tenant) and matches each transaction against `card_payment` by `stripe_charge_ref` — a match sets `matched_card_payment_id`; no match means the transaction belongs to some other system sharing that Company Code's Stripe Connected Account, not an AIARAP discrepancy to chase. Discrepancies (`amount_mismatch`, `missing_in_stripe_extract`) are logged to a dedicated `stripe_reconciliation_discrepancy` table, separate from the payout/transaction data itself.

**Timing note**: Stripe's balance-transaction day boundary is GMT/UTC midnight, not the Tenant's local business day, so matching uses a rolling grace-period window from `charged_at` rather than expecting alignment with one specific calendar day — avoids false `missing_in_stripe_extract` flags purely from UTC-cutoff misalignment.

**Grace period is per-Company-Code, not a platform constant**: each run also refreshes `company_code.stripe_payout_interval`/`stripe_payout_delay_days` from Stripe's Account API (`settings.payouts.schedule`) — self-maintaining if a Company Code's payout schedule changes directly in Stripe. The grace period is `stripe_payout_delay_days` plus a small safety margin, falling back to a 5-business-day platform default only before the first sync.

**Foreign-currency Invoices**: `stripe_payout_transaction` also captures `presentment_amount`/`presentment_currency`/`exchange_rate` for a converted charge, separating Stripe's own FX conversion from its processing fee (`fee_amount`) — comparing Stripe's rate against AIARAP's SAP-sourced `currency_exchange_rate` isolates genuine FX gain/loss from card fees, rather than blending both into one unexplained gap.

**Bucketing**: Stripe's large, growing `balance_transaction.type` enum is mapped down into a small fixed set of buckets via `stripe_transaction_type_bucket` (Tenant-editable, seeded with defaults) — `stripe_payout_transaction.transaction_type` has a real FK into it, so an unmapped new Stripe type fails extraction loudly rather than silently miscategorizing.

## Sales Order Down Payment Clearing — detail

Full design in [ADR-0029](../adr/0029-sales-order-checkout-fi-down-payment.md). Closes the loop the checkout flow leaves open: a `credit_card` Sales Order collects payment and posts an FI Down Payment *before* any Invoice exists, so something has to notice when that Invoice finally shows up and apply the down payment against it — this job is that something. `purchase_order`-method orders never enter this job at all (no `sales_order_payment` row exists for them, per that payment method's own design).

**Trigger, not a fixed periodic scan alone**: primarily event-driven — fires whenever new/updated Invoice data lands via either the Nightly Bulk SAP/Salesforce Extraction batch's "batch complete" SQS event or the Incremental Sync job, since either can be what surfaces the Invoice a pending down payment is waiting on. A daily safety-net sweep over any `sales_order_payment` row still `clearing_status = 'pending'` for more than **24 hours since `charged_at`** (parking lot item 46, resolved) catches anything the event path missed (e.g. a sync that ran before the SAP-side billing document was actually created) — younger rows are left to the event path alone, since within any 24h window it's almost certainly already had multiple chances to fire. Same "event-driven primary + scheduled safety net" shape already used for AR Reconciliation's scheduled/webhook-triggered split.

**Matching**: for each pending `sales_order_payment`, looks for an `invoice_line` where `sales_document = sales_order.sap_sales_order_id` (both fields already exist — no new lookup mechanism needed, this is the same reference SAP's own billing-document-to-Sales-Order linkage already populates on extraction). A match identifies the Invoice this Sales Order eventually became.

**On a clean match**: drives the actual down payment clearing posting in SAP via the Java service's synchronous integration API (ADR-0031) — using `sap_reference_written` (the Sales Order number AIARAP itself wrote into the down payment's own `BSEG-ZUONR`/`XREF1` at posting time) as the precise match key, the mechanism ADR-0029 relies on instead of a clerk manually clearing against the Customer's general open-item pool. On success: `sales_order_payment.clearing_status = 'cleared'`, `cleared_at` set, `matched_invoice_id` set, and a new `payment` row is inserted (`source = 'aiarap'`, `settlement_category = 'incoming_cash'`, `sales_order_payment_id` pointing back) so `invoice.open_amount` recomputes through the same derivation every other payment already uses.

**On a mismatch** (e.g. SAP's own automatic clearing already applied the down payment against a different open item before this job's check ran): `clearing_status = 'mismatch_flagged'` — surfaced to the AR Clerk (`payer_company_code.accounting_clerk_user_id`) via the Notification Channel for manual investigation, same recipient-resolution pattern as every other AR Clerk alert in this doc, rather than retried automatically (a mismatch means AIARAP's expected state and SAP's actual state have already diverged — blindly retrying risks compounding that, not resolving it).

## Automatic Bank Debit Payment Batch + Stripe Bank-Debit Webhook Sync — detail

Full design in [ADR-0032](../adr/0032-ach-sepa-bank-debit-payments.md). Mirrors the Automatic Card Payment Batch (ADR-0019) closely — same Java + Spring Batch tiering and restart-safety justification (a mid-run crash must never double-charge an Invoice), same "scan every open Invoice, resolve an eligible stored payment method, charge it" shape — but against `payer_bank_account` instead of `payer_payment_card`, and with no `payer_bank_account_payment_policy` to check (there isn't one, per ADR-0032 — only the Payer's own `self_imposed_limit_amount`/`_period` is checked as a hard outer bound before attempting a charge).

**Optimistic write-back**: unlike the card batch, a successful charge here settles over days, not instantly — but per ADR-0032's settlement-semantics decision, the SAP write-back still fires immediately on Stripe reporting the debit `'succeeded'`, not on `bank_debit_payment.settlement_status` reaching `'settled'`. Every attempt (success or failure) is logged to `bank_debit_payment_attempt`; a successful charge creates a `bank_debit_payment` row and the corresponding `payment` row (`bank_debit_payment_id` set).

**Stripe Bank-Debit Webhook Sync** is what eventually learns the multi-day outcome — and, per parking lot item 48 (resolved against Stripe's own docs), it's genuinely **two different mechanisms**, not one event-driven job:

- **Return, event-driven**: Stripe's `charge.dispute.created` webhook event is what fires when a bank debit that already looked successful comes back — for ACH, Stripe explicitly documents this exact "late failure after `succeeded`" case, with the Dispute's own `reason` field carrying `insufficient_funds`/`incorrect_account_details`/`bank_cannot_process`; SEPA's equivalent is a customer-initiated dispute (a "no questions asked" right for 8 weeks, or up to 13 months if claiming the debit was unauthorized). On this event: `bank_debit_payment.settlement_status = 'returned'`, `returned_at`/`return_code`/`return_reason` set, flips the matching `payment.status` (found via `payment.bank_debit_payment_id`) to `'reversed'`, triggers a reversal SAP write-back, and notifies the affected AR Clerk (`payer_company_code.accounting_clerk_user_id`) — the same recipient-resolution pattern as every other AR Clerk alert in this doc. **This can fire even after `settlement_status` already reached `'settled'`** — SEPA's dispute window in particular (up to 13 months) far outlasts its own settlement window (6 business days), so `'settled'` is not truly a terminal state the way it might first appear.
- **Settlement confirmation, time-based, not event-driven**: Stripe has no distinct "funds now settled" webhook — settlement is a documented time expectation (ACH: 4 business days standard, 2 days on faster settlement; SEPA: 6 business days), not a push notification. A daily sweep checks every `bank_debit_payment` still `settlement_status = 'pending'` against its method-specific window elapsed since `charged_at`; if no return has arrived by then, sets `settlement_status = 'settled'`/`settled_at` — informational only, doesn't itself trigger anything downstream (the optimistic SAP write-back already happened at charge time).

**Open items**: whether `self_imposed_limit_period = 'monthly'` uses a rolling window or calendar-month definition isn't decided.

## Sales Order Bank-Debit Confirmation Batch — detail

Full design in [ADR-0032](../adr/0032-ach-sepa-bank-debit-payments.md). This is the Sales-Order-checkout counterpart to the Stripe Bank-Debit Webhook Sync above — it reacts to the same settlement/return outcome, but for `sales_order_payment` rows (checkout-time down payments, ADR-0029) rather than direct `bank_debit_payment` Invoice payments, and its behavior branches on `company_code.bank_debit_order_confirmation_mode`, which exists precisely because the checkout flow's default (create the SAP Sales Order immediately on charge success) is riskier for ACH/SEPA than for a card: fulfillment could already be moving before the charge is actually final days later.

**`hold_in_aiarap` mode** — the charge still happens immediately at checkout (nothing about payment collection changes), but `sales_order.status` stays at `held_pending_settlement` rather than proceeding to SAP order creation. This job is what releases it:
- **Settled**: triggers the (now-deferred) SAP Sales Order creation call — `status` moves `held_pending_settlement → pending_sap_creation`, then the normal ADR-0029 flow (creation success/failure, retries, FI Down Payment posting) proceeds exactly as it would have if the charge had been a card.
- **Returned**: the order is cancelled — `status = 'held_payment_returned'`. Nothing downstream was ever created (no SAP Sales Order, no FI Down Payment, no Invoice), so unlike a direct Invoice payment's return there's no `payment` row to reverse — `sales_order_payment.settlement_status = 'returned'` is itself the terminal record of what happened.

**`submit_with_delivery_block` mode** — the SAP Sales Order is created immediately as usual, but with SAP's own Delivery Block (`delivery_block_code`) set, so a Delivery document can't be generated yet:
- **Settled**: this job calls SAP (via Java's synchronous integration API, ADR-0031) to clear the block — `delivery_block_code` set back to `NULL`, `delivery_block_cleared_at` set. Normal fulfillment can proceed from here.
- **Returned**: the block deliberately stays in place — the safe outcome, since it structurally prevents shipment rather than relying on someone reacting to a notification in time. `sales_order.fulfillment_hold_flagged_at`/`fulfillment_hold_reason` are set alongside the usual `payment.status = 'reversed'` + AR Clerk notification (ADR-0032's base case), specifically to alert whoever owns fulfillment on the Tenant side — not just AR — since a Sales Order (not just an Invoice) is implicated.

**Tier**: NestJS, primarily reacting to the Stripe Bank-Debit Webhook Sync's outcome — no independent cadence of its own for the immediate reaction.

**Daily safety-net sweep (parking lot item 53, resolved)**: unlike a missed event, the risk this sweep actually guards against is a **downstream reaction failure**, not a missed signal — `sales_order_payment.settlement_status` reaching `'settled'`/`'returned'` is itself already resilient (settlement comes from the Stripe Bank-Debit Webhook Sync's own daily time-based sweep, not a fragile webhook; return comes from `charge.dispute.created`). But that's a one-way, one-time transition on `sales_order_payment` — if this job's own reaction (triggering deferred SAP order creation, or clearing the delivery block) fails to fire right after the transition (an app-level bug or crash), nothing re-tries it, since the source table won't flip to `'settled'` a second time to give the reaction another chance. The daily sweep checks specifically for that inconsistency and re-triggers the missed action:
- Any `sales_order` still `held_pending_settlement` whose `sales_order_payment.settlement_status` is already `'settled'` or `'returned'` — the release/cancel action never ran.
- Any `sales_order` still carrying a `delivery_block_code` whose `sales_order_payment.settlement_status` is already `'settled'` — the block-clearing SAP call never ran.

Same "event-driven primary + scheduled safety net" shape already used for AR Reconciliation and the Sales Order Down Payment Clearing job.
